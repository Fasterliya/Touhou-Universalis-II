## R2-1 四档制裁所需的 modifier 字段

- **结论**：**有条件可行**。四档逐条判定结果为：
  - 第 1 档（谴责）→ **可行**，但**方向必须改写**（现有项目注释方向反了，见 b）。
  - 第 2 档（夺权）→ **可行**，但**没有任何 modifier 字段可挂**；必须改 `special_status_power` 这个 script value（这是唯一咽喉，见 c）。

**(b) "全体成员对目标的敌意/好感"最干净的落地方式 —— 附方向纠正**

方向语义的官方实证有三处，**三处一致**：

证据 1 —— `[VANILLA]\common\on_action\_hardcoded.txt:4313-4321`：
```
			# Antagonism from all Catholics for seizing the Papal capital, even if Rome is later returned
			religion:catholic = {
				every_country_in_religion = {
					limit = { this != scope:winner }
					add_antagonism = {
						target = scope:winner
						modifier = antagonism_seized_papal_capital
					}
				}
			}
```
注释写 **"Antagonism _from_ all Catholics"**（来自全体天主教徒的敌意）；执行 scope 是**每个天主教国家**（root），`target = scope:winner`（夺罗马者）。→ **root 对 target 产生敌意**。

证据 2 —— `[VANILLA]\common\country_interactions\break_others_alliance.txt:80-91`：
```
			scope:recipient = {
				add_antagonism = {
					target = scope:actor
					modifier = antagonism_ordered_me_to_annul_treaties
				}
			}
			scope:target = {
				add_antagonism = {
					target = scope:actor
					modifier = antagonism_ordered_someone_to_annul_treaties_with_us
				}
			}
```
bias 名字自证方向：`antagonism_ordered_**me**_to_annul_treaties` —— "他命令**我**废弃条约"。root（= recipient，被命令方）对 target（= actor，命令方）产生敌意。三条证据里"me / us"恒等于 `add_antagonism` 的执行 scope，即 **root**。

证据 3 —— `[VANILLA]\common\on_action\country_yearly.txt:946-951`：
```
	effect = {
		add_antagonism = {
			target = location:rome.owner
			modifier = antagonism_infidel_holds_rome
		}
	}
```
这是 country_yearly 脉冲，root = 每个天主教国家；bias `antagonism_infidel_holds_rome`（"异教徒占着罗马"）—— root 对占罗马者产生敌意。

**结论：`add_antagonism = { target = T }` 在执行 scope = A 时，语义为「A 对 T 增加敌意」。root = 产生敌意的一方，target = 被敌视的一方。**

⚠️ **与工作区现有注释相反**：`[MOD]\in_game\common\on_action\th_gensokyo_chain_events.txt:109-110` 写
```

        ### 故在扩张者（root=winner）处执行、target=受害方
```
按蓝本语义，该处代码（`:111-114` 在 root=扩张者处执行、`target = scope:loser`）实际效果是**"扩张者怨恨受害者"**，与意图（受害者及国际社会怨恨扩张者）**正好相反**。这是一个**疑似既有 bug**，需用户回实机复核（见第 4 节）。

**(c) 第 2 档"投票权归零"的机制与可行改法**

机制来源（官方 readme，最权威）：

`[VANILLA]\common\international_organization_special_statuses\readme.txt:12`：
```
#   special_status_power = <script value> the political power this group of special status countries have, relevant for io parliament issues (root = country, scope:recipient = organization, scope:source = special status)
```

**`special_status_power` 是一个完整 script value 块**，不是常数。vanilla 里两种写法都有：

- 常数 + 条件乘法：`[VANILLA]\common\international_organization_special_statuses\hre.txt:15-38`
```
	special_status_power = {
		value = 150
		if = {
			limit = { 
				OR = {
					scope:recipient = { international_organization_has_policy = policy:no_imperial_diet_policy } 
					scope:recipient = { international_organization_has_policy = policy:no_golden_bull_policy } 
				}
			}
			multiply = 1.25
		}
		else_if = {
			limit = { scope:recipient = { international_organization_has_policy = policy:hre_early_imperial_diet_policy } }
			multiply = 1.0
		}
		...
	}
```
- 引用外部 script value：`[VANILLA]\common\international_organization_special_statuses\tatar_yoke.txt:78`
```
	special_status_power = great_power_score
```

`scope:source = special status` / `root = country` / `scope:recipient = organization` → **在 `if = { limit = ... }` 里可以直接用国家触发器（含 `has_variable`）**。

MOD 侧现状：`[MOD]\in_game\common\international_organization_special_statuses\th_gensokyo_io.txt` 有 **6 个席位**，`special_status_power` **全部** 指向同一个公式 `th_gensokyo_io_vote_power_value`：`:31-33`（阎魔）、`:56-58`（守护）、`:83-85`（贤者）、`:119-121`（人类村落）、`:165-167`（幻想乡席位）、`:201-203`（普通成员）。

公式本体 `[MOD]\in_game\common\script_values\th_gensokyo_io_chain_values.txt:102-108`：
```
th_gensokyo_io_vote_power_value = {
    value = th_gensokyo_io_influence_value
    add = {
        value = th_gensokyo_io_influence_value
        multiply = modifier:th_gensokyo_io_influence_modifier
    }
}
```

**判决依据**：`country_highest_rated_special_status_power` 取该国所有席位中的**最高值**（MOD 注释 `th_gensokyo_io.txt:178` 自述；vanilla 有 `num_countries_with_special_status` / `trigger_localization\country_triggers.txt:2960` 的 `country_highest_rated_special_status_power` 触发器）。既然 6 个席位指向同一公式，**只把其中一个席位置零无效**（其余 5 个仍返回原值，最高值不变）。

| **A（推荐）** | 在 `th_gensokyo_io_vote_power_value` **公式内**加条件：`if = { limit = { has_variable = th_gensokyo_tier_2_mark } value = 0 }` | 单点改动，6 席位自动全归零；`country_highest_rated_...=0` → 议会权重 0。**必须保证任何分支都返回数字**（该项目 `:82` 注释记载过"返回 none 类型 → special_status_power 失效"的历史 bug） | 最干净，改动面 1 个文件 |

| D | 改 `policy_vote_required_vote_ratio` 等字段 | **不改单国权重**，改的是全局通过门槛，会波及所有国家 | 不符合设计 |

**改法 A 的完整写法**（保持 `else` 分支原公式，避免 none 类型）：

```
th_gensokyo_io_vote_power_value = {
    if = {
        limit = { has_variable = th_gensokyo_tier_2_mark }
        value = 0
    }
    else = {
        value = th_gensokyo_io_influence_value
        add = {
            value = th_gensokyo_io_influence_value
            multiply = modifier:th_gensokyo_io_influence_modifier
        }
    }
}
```

## R2-2 禁运 / 贸易惩罚的干净实现

- **结论**：**可行 —— EU5 有"像样的"禁运机制，不需要降级为贡金近似。** 真禁运 = `scripted_relation` `embargo_nation`（`embargo = yes`），可用 `create_relation` effect 从脚本直接施加，无需走外交行动。
- **证据**：
  - `[VANILLA]\common\scripted_relations\embargo_nation.txt:1-4` —— `"embargo_nation = {\n\ttype = diplomacy\n\trelation_type = oneway\n\tembargo = yes"`（`oneway` = 单向：first 禁运 second）
  - `[VANILLA]\common\scripted_relations\readme.txt:16` —— `"#	embargo = <yes/no> does this relationship cause an embargo between the two countries"`
  - `[VANILLA]\common\country_interactions\force_embargo.txt:77-82` —— `create_relation` 的**方向蓝本**（10 年、first=被强制者、second=被禁运者）：
```
			create_relation = { 
				first = scope:recipient
				second = scope:target 
				type = relation_type:embargo_nation
				years = 10
			}
```
  - `[VANILLA]\common\country_interactions\force_embargo.txt:7` —— 行动门槛 `"modifier:allow_diplomacy_force_embargo = yes"`（对应字段 `[MM]\…\00_modifier_types.txt:14483`）
  - `[VANILLA]\common\effect_localization\country_effects.txt:1050-1057` —— `create_relation` 是正式 effect（有本地化词条 `CREATE_RELATION_EFFECT` / `FIRST_CREATE_RELATION_EFFECT` / `THIRD_CREATE_RELATION_EFFECT`）
  - `[VANILLA]\common\scripted_relations\deny_market_access.txt:1-4` —— 第二候选：`"deny_market_access =  { \n\ttype = diplomacy\n\trelation_type = oneway\n\ttrade_to_second = -0.33"`（**连续量**贸易吸引力惩罚 −33%）
  - `[VANILLA]\common\scripted_relations\readme.txt:28-29` —— `trade_to_first` / `trade_to_second` 的官方定义：`"#	trade_to_first = <script value> increases the attraction of the first country's markets in locations belonging to the second country"`
  - `[VANILLA]\common\scripted_relations\divert_trade.txt:8-10` —— `merchant_fraction_to_first = 0.5`（商人份额转移）
- **可直接复制的写法**：
```
### 第 3 档 禁运：施加（在制裁 effect 内，任一侧 scope 均可，用 scope:first/second 明确方向）
create_relation = {
    first  = scope:target_country        # 被禁运方（receiving）
    second = scope:leader_country        # 施加方（giving）
    type   = relation_type:embargo_nation
    years  = 10
}
```
判定侧：
```
### 某国是否正被禁运
scope:target_country = { is_embargoed_by = scope:leader_country }
```
- **逐档判定表**（R2-2 的两个候选方案对比，这是本条的决策级结论）：

| | 候选 1`embargo_nation`（真禁运） | 候选 2`deny_market_access`（市场准入剥夺） |
|---|---|---|
| 实现载体 | `create_relation` + `relation_type:embargo_nation` | `create_relation` + `relation_type:deny_market_access` |
| 脚本成本 | **极低**：1 个 effect 调用，`years` 控制时长 | 极低：同上 |
| 效果强度 | 开关式（有/无），来自引擎 `embargo = yes` | **连续量**：`trade_to_second = -0.33`，可按需新写一个 relation 调数值 |
| 是否影响 AI 决策 | **会**：`relation_type_for_ai = hostile`（`embargo_nation.txt:12`），AI 会把对方当敌对处理 | **会**：`relation_type_for_ai = hostile`（`deny_market_access.txt:12`） |
| 是否影响无关国家 | **基本不**。唯一外溢：`deny_market_access.txt:52-88` 的 `offer_effect` 会让**其他使用该市场的商人**对施加者产生恶感（`opinion_annoyed_about_denying_market_access`）；`embargo_nation` 无此外溢 | 同上，**且外溢更明显**（按商人势力加权 `scale`，`max = 2`） |
| 可否被解除 | 能：`will_expire_trigger`（`embargo_nation.txt:44-46`，结盟即失效）+ `break_enabled` 需 CB 且无停战 | 能：`will_expire_trigger`（`deny_market_access.txt:45-50`） |
| 副作用/风险 | `offer_enabled`（`:20-42`）含多项前置（非盟友、非附属、无 `lifts_trade_protection`）。**`create_relation` 是否绕过 `offer_enabled` 未经证实【不确定】** —— 若引擎校验，制裁施加可能静默失败 | 同左 |
| 推荐 | ✅ **主方案** | 备用（想要"连续量贸易惩罚"时用） |
- **语义边界与坑**：
  1. **方向**：`relation_type = oneway`，`first` = 给出关系的一方。`force_embargo.txt` 的蓝本把 `first = scope:recipient`（被强制去禁运的国家），说明 **first 是"禁运发起方"**，`second` 是"被禁运方"。审判庭场景下若想让**被诉国**被全乡禁运，则所有成员都应是 `first`，被诉国是 `second`；若只想让**被诉国**去禁运别人，方向相反。**这是最易写反的地方。**
  2. `[VANILLA]\common\country_interactions\force_embargo.txt:52-56` 用 `can_add_relation` 触发器做 UI 可见性判定 —— 说明"创建关系"在引擎里有前置校验概念。**脚本 `create_relation` 能否跳过这些校验，必须实机验证**（建议先做一个最小测试行动）。
  3. `embargo_nation` 的 `break_enabled`（`:48-53`）要求 `has_casus_belli_on` 且无停战 —— 意味着**解除禁运不是免费的**，设计上"赦免"若要走外交解除会受到限制；**直接 `remove_relation` 类 effect 的可能性未验证【不确定】**。
  4. `relation_type_for_ai = hostile` 会改变 AI 的长期行为（视对方为敌），**这正是"经济制裁"应有的味道，属于正向副作用**，但需要在设计上确认接受。
- **退路**（若 `create_relation` 实机失败）：
  1. **贡金近似**（设计原退路）：每月 `gold` 转移（`scripted_relations\readme.txt:30-31` 的 `gold_to_first` / `gold_to_second` 是同类思路）+ `add_opinion` 恶感 + 挂 `trade_income` 负修正。**可行性高**（`trade_income:6675` 已验证存在），但观感弱于真禁运。
  2. **修正近似**：给被诉国挂 `trade_isolation = yes`（`:11382`，boolean，开关式）+ `trade_land_efficiency = -0.25`（`:10274`）/ `trade_sea_efficiency = -0.25`（`:10282`）。这是**全局**贸易效率下降，**无法只惩罚"与被诉国的贸易"**，会误伤无关国家 —— 副作用比候选 1 大。
  3. **走既有国交行动**：直接复用 vanilla `force_embargo` 的机制（需给阎魔挂 `allow_diplomacy_force_embargo = yes`，`:14483`），由玩家/AI 手动点。**零新增脚本**，但不可自动化、不可控。
- **对《脚本规格》/《实施计划》的影响**：
  - 《实施计划》§4 待验证 2 → **本报告结案**：有干净实现，**不必降级为"贡金 + 好感惩罚"**。
  - 《脚本规格》§7.3 第 3 档"贸易惩罚 / 贡金" → 建议改为"**禁运关系（embargo_nation）+ 可选贡金**"。
  - 《脚本规格》§8 `th_embargo_trade_penalty_value = 0.25` → 该连续量在 `embargo_nation` 里**无处安放**；若要连续量，应改用 `deny_market_access` 并新增一个自定义 relation（`trade_to_second = -0.25`）。

**(b) 能否按"目标国当前制裁档位"动态改价？**

**能。** 链路：`price_modifier` 是计算值 → 其 `if = { limit = { <triggers> } }` 支持触发器 → `has_variable` 在 script value 的 limit 里可用（**已验证**：`[VANILLA]\common\script_values\io_policy.txt:341` `"limit = { scope:recipient = { has_variable = hre_imperial_religion_group } }"`，`:890` 同构）。

- **方案 A（推荐，1 个价格键 + 动态修正）**：
```
price = price:th_gensokyo_confess_price
price_modifier = {
    value = 1
    if = {
        limit = { scope:actor = { has_variable = th_gensokyo_tier_1_mark } }
        multiply = 1.0
    }
    if = {
        limit = { scope:actor = { has_variable = th_gensokyo_tier_2_mark } }
        multiply = 1.5
    }
    if = {
        limit = { scope:actor = { has_variable = th_gensokyo_tier_3_mark } }
        multiply = 2.0
    }
    if = {
        limit = { scope:actor = { has_variable = th_gensokyo_tier_4_mark } }
        multiply = 2.5
    }
}
```
（系数对应《脚本规格》§4.5 的"基础价 ×（1 + 0.5 × 档数）"）

- **方案 B（退路，4 个价格键 + 行动内分流）**：`price = price:th_gensokyo_confess_price_t1` 等 4 键，但 `price` **只能写一个**，无法按条件切换 —— 所以方案 B 实际上**必须靠 4 个不同的 generic_action**（各写死一个价），**而不是"一个行动内分流"**。《脚本规格》§4.5 描述的"行动内按档位判断后分别扣款"需要 `should_execute_price = no` + 手动 `add_gold`/`remove_gold`，**成本远高于方案 A**。

  → **结论：方案 B 的可行性低于《脚本规格》的假设，建议直接采用方案 A。**

**(c) `currency = gold` / 其他货币字段是否存在？**

**`currency` 字段不存在** —— `generic_actions` 全库搜 `^\s*currency\s*=` **0 命中**；`prices\readme.txt` 的 32 行字段表里也没有 `currency`。

**"货币"是通过 `prices/` 的字段名表达的**，即上表里的 `gold` / `scaled_gold` / `scaled_recipient_gold` / `gold_per_pop` / `manpower` / `sailors` / `prestige` / `stability` / `inflation` / `war_exhaustion` / `government_power` / `karma` / `honor` / `doom` / `purity` / `rite_power` / `yanantin` / `complacency` / `righteousness` / `harmony` / `self_control` / `religious_influence` / `army_tradition` / `navy_tradition`。

**结论：认罪价用 `gold = <值>` 即可（照 `th_gensokyo_feast_price.txt:6`）。** 若要"用威望/稳定度抵罪"，直接换成 `prestige = <值>` 或 `stability = <值>`，**不需要 currency 字段**。另有 `min` / `min_scale` / `max_scale` 三个钳制字段可用于"认罪价不低于 X"。

- **语义边界与坑**：
  1. `price_modifier` 的语义是 **"乘数"**（readme 原文 "multiplies the price"），不是加数。写 `add = 100` 会变成"价格 +100 倍"式的错误理解。**乘法请用 `multiply`**；`add`/`divide` 作用在乘数本身（如 `add = { value = 1 ... }` 使乘数从 0 起变为 1）。
  2. `bureaucracy_actions.txt:25-39` 的根表达式是 `add = { value = 1 ... }` —— 即**乘数基线 1**（原价）。若只写 `if = { limit = ... multiply = 2 }` 而不给基线，乘数可能从 0 起算 → 价格归零。**必须给基线**。
  3. `scope:actor` 在 `price_modifier` 里可用（readme `:12` 明写），所以读 `scope:actor` 身上的档位标记是正确的 scope。
  4. `prices\readme.txt:29` 的 `min = <float>` 是"**修正后合计的最低值**"，`min_scale` / `max_scale` 是"**修正前**你要付的量"——三者语义不同，别混用。
  5. `price = <裸 script value 名>`（`ilkhanate_actions.txt:20`）与 `price = price:<key>` 是**两套不同命名空间**。MOD 现有 `th_gensokyo_feast_price` 是 `prices/` 条目 → 必须写 `price = price:th_gensokyo_feast_price`。
- **退路**：若 `price_modifier` 实机对 `has_variable` 不生效（**未实机验证，风险低但存在**），退路 = `should_execute_price = no` + 在 `effect` 内用 `scope:price` 读原价、自行按档位 `remove_gold`（readme `:72` 确认 `scope:price` 在 effect 内可用）。
- **对《脚本规格》/《实施计划》的影响**：
  - 《脚本规格》§4.5「花费载体」待验证 3 → **本报告结案**：用**方案 A**（单价格键 + `price_modifier` 动态系数），放弃"四个固定价格键"。
  - 《脚本规格》§9 待验证 3 → **本报告结案**。
  - 《脚本规格》§9 待验证 8（`show_in_gui_list`）→ **顺带结案：字段存在**（`generic_actions\readme.txt:68`）。

**(b) AI 如何选择 option？权重字段叫什么、以什么 scope 求值、能否引用变量/标记？**

- **字段**：`ai_will_select`（script math，**优先**）与 `ai_chance`（MTTH 式）。
- **求值 scope**：与 option 的 `trigger` / effects 相同，即 **事件 `type` 定义的 root scope**（`events\readme.txt:89` 明写 `root = defined scope from type`）。对本任务 = 收到事件的**被提名国**。
- **运作方式**（wiki `Event_modding` §"AI selection modding"）：
> "`ai_will_select` and `ai_weight` are both used for AI to determine which option will be picked. If both are available, `ai_will_select` will be used. Both of them provide the AI with a weight of the option which is selected according to weighted randomness: … # Total weight of all options is 100 + 30 + 20 = 150 # The chance of AI picking option a is 100 / 150 = ~67%"
> "`ai_will_select` determines the value by using a scripted value, while `ai_weight` uses 'mean time to happen'-like syntax."
- **能否引用变量/标记？** **能。** vanilla 事件实例 `[VANILLA]\events\hre.txt:58-80` —— `ai_chance` 的 `modifier` 里直接用 `has_variable`：

```
		name = hre.101.a
		ai_chance = {
			factor = 10
			modifier = {
				factor = 0
				NOT = { has_variable = voted_for_privilegia }
			}
		}
		add_opinion = {
			target = international_organization:hre.leader_country
			modifier = opinion_hre_passed_opposed_law
		}
	}
	option = {
		name = hre.101.b
		ai_chance = {
			factor = 10
			modifier = {
				factor = 0
				has_variable = voted_for_privilegia
			}
		}
		...

```
  这条实例同时证明三件事：① `ai_chance` 的根键可写 **`factor`**（不只 readme 的 `base`）；② `modifier` 块内的键是 **`factor`**（readme 写 `add`，两者都能被解析）；③ **`has_variable` 可直接作为 `ai_chance` 的触发器**。

**(c) 事件对"玩家国家也可选"场景，AI 与玩家分支怎么写？**

vanilla 的写法是**同一个 `option` 块同时服务玩家和 AI**，靠 `ai_chance` / `ai_will_select` 只在 AI 决策时生效；玩家看到全部可用 option 自行点选。**不需要为玩家单写分支。**

```
                desc = "RELATIVE_STRENGTH"
                value = th_gensokyo_agent_acceptance_value
            }
        }
        th_gensokyo_tribunal_agent_accept_effect = { }
    }
    option = {
        name = th_gensokyo_tribunal_events.1.b          # 拒绝领衔
        ai_will_select = {
            value = 50
            if = {
                limit = { has_variable = th_gensokyo_agent_refused }

            }
        }
```

**(d) 若 EU5 没有 option 级 AI 权重，退路是什么？**

**该退路不需要启用** —— option 级 AI 权重**存在且有两套**（`ai_will_select` + `ai_chance`）。本节仅按要求列出最低风险退路作为预案：

1. **最低风险退路（推荐备用）：路径 B —— 脚本判定 + 事后抗命行动**（即《脚本规格》§4.2 的"路径 B"）。
   理由：① 完全绕开事件 AI 决策的不确定性；② 项目已有 `th_gensokyo_tribunal_agent_refuse`（§4.9）作为事后出口；③ `ai_will_do` 已被本报告 R2-5 证明**可读 `has_variable` 与 `var:`**，所以脚本判定 `th_gensokyo_agent_will_accept_trigger` 是可靠的。
2. **次低风险：事件只发给玩家，AI 走脚本判定**。做法：`th_gensokyo_tribunal_escalate` 的 `effect` 内用 `if = { limit = { scope:agent_country = { is_ai = yes } } <脚本判定> else = { <trigger_event> } }`。**代价 = 两套逻辑，维护成本翻倍**，不推荐。
3. **不推荐：把"接受/拒绝"做成两条 generic_action**。generic_action 的 `potential`/`allow` 天然是"发起方"视角，**外部国家无法被强制弹出一个行动**，无法实现"征求同意"的被动语义。

- **语义边界与坑**：
  1. **字段名冲突（必须记录）**：wiki 说 `ai_weight`；vanilla `events\readme.txt:102` 说 `ai_chance`；vanilla 事件实际 188 处 `ai_will_select` + 1213 处 `ai_chance`，**`ai_weight` 在 `[VANILLA]\events\` 下 0 命中**（`ai_weight` 只出现在 `common\advances\`、`common\estate_privileges\`、`common\unit_categories\`，是**别的系统**的字段）。**以 vanilla 为准：事件 option 用 `ai_chance` / `ai_will_select`，不要写 `ai_weight`。**
  2. `ai_chance` 与 `ai_will_select` 的关系是**覆盖**：readme 原文 "Overrules ai_chance"。**两者同时存在时只有 `ai_will_select` 生效。**
  3. `ai_will_select` 的根键是 **`value`**（script value 语义），不是 `base`；`ai_chance` 的根键可以是 **`base`**（readme）或 **`factor`**（vanilla 实例）。
  4. `show_as_unavailable` **未实现**（readme `:110`）—— 不要用它做"不可选但可见"的灰置选项。

## R2-5 `ai_will_do` 能否读 `has_variable` / 变量

- **结论**：**成立 —— 项目 `th_gensokyo_feast.txt:136` 的那条限制不成立（过度概括）。**
  - `ai_will_do` **能**用 `has_variable = X` 这种判存在的触发器（vanilla 有直接实例）。

  4. `take_over_wars_when_called`（readme `:104`）是**相邻但不同**的机制："领袖以共同交战国身份入战时自动接管为战争领袖"。**若想让代理人当战争领袖，这条的思路更接近（让代理人以 co-belligerent 入战）**，但它同样是 IO 定义字段，且需要 `joins_*_wars_as_co_belligerent` 配合。**其实际效果未实机验证【不确定】。**
- **退路**：**接受现状**（《实施计划》§4 待验证 5 已定"领衔 ≠ 战争领袖，功能不受影响，影响观感不阻塞"）。本报告**同意该判断**，并补充：观感可在 UI 上补偿 —— 在审判庭面板用关系图/成员列表高亮代理人（`th_gensokyo_tribunal_agent_mark`），让"领衔"在**界面**上可见，而不依赖战争领袖位。
- **对《脚本规格》/《实施计划》的影响**：
  - 《实施计划》§4 待验证 5 → **本报告结案为 FAILED（语义不可查）**，维持"接受现状"结论。
  - 《脚本规格》§4.8 备注「若需强制代理人当战争领袖，属独立改动」→ **应改为"引擎不支持，无法实现"**，避免后续为一个不存在的能力排期。
  - 《实施计划》§1.2「确认 `promote_strongest_member_to_war_leader`（35 行）与代理人标记的关系」→ **结案：无交互，可并存。**
